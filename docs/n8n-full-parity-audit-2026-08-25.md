# Full n8n parity audit — 2026-08-25

## Verdict

Backstory Studio is **not at full n8n parity**. It has a credible workflow product, a strong free-form editor, durable execution, unusually good safety controls, and substantial AI-agent functionality. Those strengths do not close the largest compatibility gaps:

1. n8n's universal item-array, paired-item, binary, and typed-port execution contract is not reproduced.
2. Backstory has no per-node behavior versions and no populated breaking-change impact/migration product.
3. n8n's metadata-driven node configuration system is much broader than Backstory's hand-authored node forms.
4. n8n declares 564 nodes and 445 credential types. Backstory has 22 consolidated flow node types, 17 curated Nango providers, and 55 curated provider operations; generic HTTP and MCP extend reach but do not provide first-class parity.
5. Data Tables, hosted Forms, dynamic per-user credentials, external secret stores, source-control environments, workflow OpenTelemetry, and numerous protocol/utility nodes are absent.
6. Backstory's served MCP endpoint is materially behind n8n's current protocol, transport, scope, configuration, and management-tool surface.
7. Backstory's flow copilot and agent runtime are substantial, but n8n's Instance AI, Agents SDK, LangChain-node catalogue, Chat Hub, channel breadth, and productized evals are larger and more configurable.

The previous documents `docs/flows-n8n-parity-audit.md` and `docs/n8n-platform-parity-audit-2026-08-25.md` should not be used as the current baseline. Several of their gaps have since been implemented, while several “closed” findings only matched a feature name rather than n8n's runtime semantics.

## Method and confidence rules

This audit does not equate directory size, a matching filename, an import adapter, or generic API reach with parity.

Evidence was collected at four levels:

1. **Declared-surface enumeration.** Both n8n package manifests were parsed. Every declared node and credential entry is present in the JSON inventory with its package, declared path, source path, family, inferred trigger/tool kind, and conservative Backstory assessment. Every top-level CLI module and editor feature directory is also inventoried with file and source-line counts so a module cannot disappear from scope merely because it was not on an initial shortlist.
2. **Contract comparison.** The core workflow interfaces, data proxy, node setting types, Backstory graph schema, scheduler, interpreter, step persistence, expression resolver, and node forms were compared as runtime contracts.
3. **Deep source review of high-risk features.** HTTP, Merge, Wait, Data Tables, breaking changes, Agents, Instance AI, MCP, Chat Hub, dynamic credentials, OAuth server, workflow SDK, engine-v2, execution UI, source control, external secrets, log streaming, and OpenTelemetry were opened beyond their directory listings.
4. **Capability matrix.** Each material runtime, node, configuration, editor, agent, MCP, credential, and platform feature was assigned `strong`, `partial`, `gap`, `intentional-divergence`, `ahead`, or `not-benchmark`, with evidence paths and the mismatch stated.

“Full audit” here means complete declared node/credential accounting plus a complete workflow-platform capability map. It does **not** mean that every one of 27,268 n8n files was read line by line. The inventory deliberately avoids pretending that file count is semantic analysis.

## Corrections to the earlier audits

The current source disproves several earlier conclusions:

- **The editor is no longer chain-only.** `src/components/flows/canvas/graph-canvas.tsx` provides a free-positioned React Flow graph with manual edges, multi-select, copy/paste, minimap, zoom, fit, tidy layout, disconnected nodes, and live collaboration state.
- **Execution is not generally inline.** `src/features/flows/execute-flow.ts`, `src/lib/queue`, and `src/lib/workers/runtime.ts` use BullMQ and a worker in normal deployment. The remaining inline durability gap is specifically the synchronous last-node webhook response path.
- **A real definition review gate exists.** `FlowReview`, review routes, graph fingerprints, second-person approval, and the publish gate are implemented.
- **Backstory now serves MCP.** `src/app/api/mcp/route.ts` exposes published flows and run polling as MCP tools. Its protocol and management breadth remain partial.
- **The agent system is not one file pretending to match a module.** It has durable transcripts, resume, model fallbacks, memory, tools, approvals, subagents, budgets, egress policy, replay protection, chat sessions, schedules, and Slack bindings. It still does not match the full n8n agent platform.
- **Breaking changes are not “95 rules.”** The audited n8n module contains 96 files but 36 rule files and one automatic migration (`ai-transform-to-code`). File count was previously confused with rule count.
- **n8n engine-v2 is not the stable parity target.** At this commit it is experimental, does not support queue mode, and still has credential/admission TODOs. Stable n8n execution behavior remains the benchmark.

The older “all Tier 1 and Tier 2 gaps closed” conclusion is still wrong. In particular, opt-in `perItem` support does not close n8n's universal item-pipeline semantics.

## Architecture and runtime findings

### 1. The item model is the central semantic gap

n8n's `INodeExecutionData` carries `json`, `binary`, `error`, `pairedItem`, and metadata for every item. `WorkflowDataProxy` uses run index, item index, connection input data, and paired lineage to make references such as the current matching upstream item meaningful.

Backstory's `FlowContext` carries arbitrary values under trigger, step, item, loop, variables, time, and run metadata. `perItem` executes a selected node once over a chosen list and collects outputs. That is a useful product abstraction, but it does not establish:

- a universal array-of-items contract between every node;
- corresponding-item lineage across splits, merges, branches, and named-node references;
- a binary payload map per item;
- typed/indexed input and output ports;
- n8n run/item indices and node context semantics.

Consequence: a workflow can appear structurally imported and still change meaning when it relies on item pairing, multiple input indices, binary properties, or expressions tied to the current item. This is a high-impact compatibility boundary, not a small node gap.

### 2. Graph topology is intentionally narrower

Backstory now supports a genuine free-form DAG with fan-out and fan-in. Its validator nevertheless rejects outer-graph cycles. Loop and parallel behavior live in explicit container nodes, and branching inside those containers has restrictions.

n8n workflows can encode loop-back connections and use item/run behavior around those connections. The importer explicitly drops a connection that would close a cycle and records a warning. This is transparent degradation, not parity.

### 3. Expressions are partial, not equivalent

Backstory's resolver safely supports dot-path tokens over incoming data, trigger data, steps, the steps aggregate, items, loop indices, variables, frozen time, flow identity, and run identity. Exact tokens preserve object/array values.

n8n's data proxy supplies a much broader execution environment with JavaScript expressions, input and node accessors, run/item indices, workflow/execution metadata, environment and variables, date/time objects, paired-item resolution, JMESPath, and node context. Backstory's n8n importer can hoist some JavaScript expressions into Code nodes and warns on untranslatable runtime values, but that does not make the ordinary parameter expression engines equivalent.

### 4. Durability is strong, with one important webhook exception

Backstory's queued execution, graph snapshots, step persistence, wait/resume, immutable dependency manifest, side-effect ledger, idempotent scheduling claims, and cancellation state are strong. The dependency manifest and cross-tool side-effect replay ledger are areas where Backstory is ahead of the comparable n8n surface inspected.

The public webhook's default last-node response path still waits on `runFlowExecution` inline so it can return the output on the same request. A request timeout or serverless lifetime can therefore strand the synchronous caller even though other execution paths are queued. n8n separates webhook and worker responsibilities and has response routing infrastructure for this case.

### 5. Version compatibility is only scaffolded

Backstory stores `schemaVersion` and preprocesses graphs through `migrateGraphShape`, but the current version is 1 and the migration list is empty. n8n stores `typeVersion` on each node, keeps legacy implementations, and separately scans workflows/instance settings for known breaking changes.

n8n's breaking-change module provides batched scans, affected-workflow details, recommendations, refresh/report APIs, and migration endpoints. Backstory has no equivalent impact report. A global graph version is not a substitute for independent node versions.

## Node configuration framework findings

n8n's official `NodePropertyTypes` union contains 25 types: boolean, button, collection, color, dateTime, fixedCollection, hidden, icon, json, callout, notice, multiOptions, number, options, string, credentialsSelect, resourceLocator, curlImport, resourceMapper, filter, assignmentCollection, credentials, workflowSelector, and agentSelector.

Its metadata also drives display conditions, dependencies, load options, list searches, min/max constraints, multiple values, sorting, password handling, code/SQL editors, resource mapping, filters, assignments, and binary-property selection.

Backstory's `step-drawer.tsx` provides carefully authored controls for its own 22 node types, and `tool-schema.ts` parses a useful subset of JSON Schema including references, unions, enums, defaults, nullability, bounds, objects, and arrays. The mismatches are structural:

- arbitrary n8n node descriptions cannot be rendered;
- nested object/array tool values fall back to JSON text;
- identifier pickers are heuristic rather than explicit resource-locator metadata;
- there is no general resource mapper;
- there is no cURL import property;
- loadOptions/listSearch/displayOptions are not general node metadata contracts;
- credential selection is split across purpose-built HTTP, integration, and MCP forms;
- generic `executeOnce`, node-version upgrade UI, and full notes/version documentation are absent.

The Backstory forms may be better for the smaller native catalogue. They are not a compatible implementation of n8n's extensible parameter system.

## Native node findings

Backstory's 22 native node types are:

`trigger`, `agent`, `condition`, `loop`, `parallel`, `stop`, `tool`, `http`, `transform`, `filter`, `switch`, `variable`, `data`, `code`, `humanReview`, `output`, `join`, `ai`, `subflow`, `knowledge`, `wait`, and `note`.

The catalogue covers the most important workflow primitives. The exact node-by-node disposition is in the generated JSON. The largest first-class gaps are:

- permanent Data Tables and their table/column/row CRUD node;
- Form and Form Trigger, including form-based wait/resume;
- SSE and protocol-specific event triggers;
- Compare Datasets;
- Compression/archive operations;
- Crypto, JWT, and TOTP utilities;
- FTP/SFTP and SSH;
- database nodes with query, transaction, insert/update, mapping, and credential behavior;
- Kafka, RabbitMQ, AMQP, MQTT, IMAP, RSS, and filesystem triggers;
- workflow-authored evaluation and simulation nodes;
- the separate binary and spreadsheet operation breadth.

Execute Command and local filesystem triggers are intentional hosted-product divergences because Backstory's code runners deny child processes, imports, files, and network access.

### HTTP Request

Backstory supports seven HTTP methods, generic/predefined auth, query and headers, JSON/raw/GraphQL/form-urlencoded/multipart/text bodies, file references, auto/JSON/text/file response handling, SSRF checks across redirects, retry, timeout, per-item execution, pagination, and AI response optimization.

Missing or different n8n v3 capabilities include SSL certificate credentials, field-versus-JSON parameter modes across sections, native batching controls independent of `perItem`, ignore-SSL, query array formatting, lowercase-header handling, output headers/status placement, “never error,” arbitrary pagination updates to body/header/query parameters, expression completion conditions, proxy settings, cross-origin credential behavior, and HTML CSS-selector optimization. Some omissions—proxying and ignore-SSL in particular—may be intentional security decisions.

### Merge

Backstory implements passthrough, append, combine by key, combine by position, and all combinations, with an include-unpaired option.

n8n Merge v3 additionally supports SQL, choose-branch behavior, 2–10 inputs where applicable, matching on multiple or different-named fields, fuzzy comparison, first/all multiple matches, keep matches/nonmatches/everything/enrich modes, output-side selection, clash suffix/preference rules, deep/shallow merge, and empty-value override control.

### Wait

Backstory supports duration, specific time, and resume-webhook modes with optional timeout. n8n additionally supports form submission, inbound basic authentication, webhook suffix configuration, response/attribution settings, and richer wait-limit configuration.

## Integration and credential findings

Backstory's 17 curated providers are GitHub, Linear, Jira, Asana, Notion, HubSpot, Confluence, Zendesk, Monday, Google Drive, Google Sheets, Slack, Gmail, Salesforce, Airtable, Figma, and Granola. Together they expose 55 curated operations.

n8n's 442 base entries include core nodes plus hundreds of application nodes and triggers. The gap is not adequately described by subtracting 17 from a directory count:

- for an overlapping provider, Backstory commonly exposes 2–5 curated actions while n8n exposes resources, operations, triggers, dynamic options, pagination behavior, credential variants, versions, and provider-specific UX;
- generic HTTP makes an API reachable but does not supply an operation catalogue, resource mapping, trigger state, credential testing, or migration behavior;
- generic MCP only helps when the user has an appropriate server and does not reproduce the original node's contract;
- the n8n importer preserves unsupported applications as an unbound tool, direct HTTP step, pass-through Code stub, or Note and records fidelity warnings. That is good import hygiene, not runtime parity.

All 445 n8n credential entries are enumerated in the JSON inventory. Backstory's encrypted HTTP credentials, Nango accounts, integration secrets, and MCP auth are strong security primitives, but they do not implement the 445 n8n field schemas, OAuth variants, authentication injection rules, test requests, display conditions, and node bindings.

## Editor and execution UX findings

Backstory is strong in the day-to-day canvas:

- free positioning and connections;
- multi-select, copy/paste, minimap, fit, tidy, zoom;
- live collaborator cursors and dragging;
- pin data and per-run state overrides;
- execute-to-node and fork-with-edits;
- structured table/JSON search plus raw/rendered outputs;
- live agent process feeds and step timings;
- draft edit snapshots, published versions, summaries, restore, and definition review.

Remaining n8n UX gaps include:

- a truly metadata-driven node detail view;
- the full expression editor/data-proxy preview;
- execution filters for mode, dates, workflow, custom data, annotation tags, and ratings;
- execution annotations, votes, and tags;
- searchable custom execution metadata;
- exact retry-original versus retry-current lineage;
- node type/version upgrade warnings and node-version documentation;
- a public typed workflow SDK with fluent builders, generated node definitions, code/JSON round-trip, validation, lint, CLI, and code generation.

Backstory's n8n importer is far more capable than a shallow file-name audit suggested. It maps core structural nodes, AI chains and agent clusters, selected application operations, pin data, node settings, expressions, Code compatibility helpers, files, transforms, and positions. It also explicitly reports lost cycles, unsupported expressions, credentials, triggers, and nodes. Because those reports exist, imported does not mean equivalent.

## AI, agents, and Instance AI findings

### Agents

Backstory's agent runtime is substantial. Source review found durable transcript checkpoints and resume, model fallback/circuit breaking, token budgets, AI egress enforcement, Nango/MCP/HTTP tools, skills, bounded subagents with cycle prevention, run-flow tools, knowledge/graph/memory retrieval fenced as untrusted data, approvals, exfiltration guards, tool replay protection, human questions, reflection, chat sessions, schedules, and Slack channel bindings.

n8n's corresponding surface spans `packages/cli/src/modules/agents` (438 files), `packages/@n8n/agents` (596 files), frontend agent features, LangChain nodes, and agent evals. Material gaps are:

- a public fluent Agent/Tool/Memory/Guardrail/MCP/Eval/Telemetry SDK;
- provider/model breadth;
- Telegram, Discord, Linear, and n8n-chat channel adapters in addition to Slack;
- explicit observation and episodic-memory abstractions and controls;
- pluggable vector stores, retrievers, rerankers, loaders, splitters, parsers, and model selectors;
- productized agent eval datasets, case generation, comparisons, ratings, and UI;
- provider-wide tracing and telemetry integrations.

Backstory is strong in safety and replay controls, especially its integrated AI egress policy, confused-deputy fencing, owner-scoped credentials, cross-tool side-effect ledger, and immutable execution manifest. The side-effect ledger and immutable manifest are the two areas this audit classifies as ahead. Those strengths do not erase the configurability and product-surface gaps.

### Instance AI and flow copilot

Backstory's copilot grounds the current graph, validation, roster, and tool catalogue and applies sanitized add/update/delete/move/trigger/replace operations.

n8n's Instance AI spans backend, shared package, and editor modules. It has domain tools for workflows, executions, credentials, Data Tables, workspace research, documentation, nodes, files, testing, and building; task/checkpoint orchestration; credential binding; workflow SDK generation; and verification/simulation loops.

Therefore the correct result is partial flow editing, not Instance AI parity. A separate internal Backstory issue also exists: the copilot's operation/type allowlists do not expose every native graph type consistently, including `wait`, `note`, and parts of the `code` contract.

Computer Use is also a real, separate gap rather than an off-mission filename. n8n includes `@n8n/computer-use`, an Electron local gateway, a browser extension, WebSocket/CDP relays, capability negotiation, and Instance AI prompts/guards for filesystem, shell, browser, screenshot, and mouse/keyboard tools. Backstory has no user-device gateway or browser-automation runtime. Airtop remains a separate declared browser-automation integration node and is classified as generic fallback only in the node inventory.

### Chat Hub

Backstory has agent chat sessions and messages. n8n Chat Hub additionally provides a unified provider/model/workflow conversation service, per-session tool selection, regenerate/edit/stop behavior, production and manual conversation modes, workflow wait resumption, title generation, streaming state, and file attachments with MIME policy and binary storage. Backstory is partial here and lacks the comparable chat attachment surface.

## MCP findings

Backstory is a capable MCP client. It supports server discovery, Streamable HTTP consumption, tool schemas, verification/health, API keys, OAuth client credentials, OAuth authorization code with PKCE, token refresh, encrypted secrets, and SSRF protection.

Its MCP server is much narrower:

- fixed protocol `2024-11-05` rather than n8n's audited `2026-07-28` server revision with compatibility handling;
- plain JSON-RPC POST rather than the fuller Streamable HTTP/session behavior;
- no protocol routing headers used by n8n for gateways and policy;
- only published-flow tools plus `get_flow_run`;
- no folders, projects, workflow CRUD, versions/diffs/restore, credential listing/assignment, node exploration, validation, testing, Data Tables, agent references, skills, or instance settings tools;
- no per-workflow `availableInMCP`, instance redirect settings, or comparable MCP scopes/settings product.

## What is intentionally not called a gap closure

The following substitutions are useful, but this audit refuses to count them as full parity:

- “Can call the REST API with HTTP” is not a first-class application node.
- “Could connect an MCP server” is not the same operation, trigger, credential, and configuration contract.
- “Imports as a stub with a warning” is not executable equivalence.
- “Has an agent” is not Agents SDK, LangChain-node, channel, eval, and Chat Hub parity.
- “Has `schemaVersion`” is not per-node version compatibility and a breaking-change report.
- “Can loop over a list” is not paired-item lineage and the universal item pipeline.
- “Has encrypted secrets” is not dynamic credentials or external secret stores.
- “Has versions” is not Git-backed source-control environments.
- “Has logs” is not OpenTelemetry workflow tracing.
